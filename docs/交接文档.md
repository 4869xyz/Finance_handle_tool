## 1. 项目是什么

这是一套**前后端分离的内部财务工具**，用来减轻员工报销资料的人工录入和核对。

当前产品有三条互不替代的能力：

| 入口 | 页面 | 用途 | 是否仍在用 |
|------|------|------|------------|
| 单张发票 | `/upload`、`/`、`/invoices/:id` | 一张增值税发票：OCR + Vision LLM 双源识别、差异人工确认 | 保留，独立账本 |
| 单月目录 | `/batches` 中部「单月目录」 | 选员工 + `YYYY-MM`，上传含 `发票` / `补票` / `支付凭证` 的一个月文件夹 | 保留 |
| 报销提交包 | `/batches` **顶部** | 一次上传 `姓名-报销` 大文件夹（`*报销总表.xlsx` + 多个月度目录），按月拆成现有识别批次，总表右侧写出「系统审核」列 | **当前主路径（v0.5）** |

公司档案在 `/settings/company-profile`，用于发票购买方抬头核验；未配置时发票会按放宽规则保留，并提示抬头无法严格核验。

**明确不做（当前范围外）**：视频内容识别、图片相似去重、税务真伪 API、审批流、ERP 对接、专票/普票交叉核对。第一阶段也不提供批次文档字段的在线编辑/确认 API，人工复核只是可查询的工作队列。

## 3. 5 分钟启动

技术栈：React 18 + Vite + Ant Design / FastAPI + SQLAlchemy 异步 / PostgreSQL 16 / PaddleOCR / 多厂商 Vision LLM。编排见根目录 `docker-compose.yml`。

### 3.1 首次

```powershell
# 项目根目录
Copy-Item backend/.env.example backend/.env
# 编辑 backend/.env：确认 DATABASE_URL；需要月度识别时再填 LLM Key
docker compose up -d
docker compose ps
```

容器共四个：`invoice_db`、`invoice_backend`、`invoice_ocr_worker`、`invoice_frontend`。

| 服务 | 地址 |
|------|------|
| 前端 | http://localhost:15173 |
| 后端 Swagger | http://localhost:18080/docs |
| 健康检查 | http://localhost:18080/api/health |
| 数据库 | `localhost:5435`（容器内 `5432`，库 `invoice_db`，用户/密码默认 `postgres/postgres`） |

更短的端口备忘见根目录 [`caozuo.md`](../caozuo.md)。Cursor 日常操作见 [`Cursor项目规范使用流程.md`](./Cursor项目规范使用流程.md)。

### 3.2 配置 LLM

月度资料和提交包依赖 LLM（交易拆分、难例 vision、跨文件核对、审核分类）。旧单发票可以只开 OCR。

1. 把对应厂商 Key 写入 `backend/.env`（当前默认示例是通义千问 `qwen3.7-plus`）
2. 或在前端打开 LLM 配置弹窗，走 `/api/settings/llm/*`
3. `LLM_CONFIG_TOKEN` 非空时，配置接口需要请求头 `X-LLM-Config-Token`

国内环境常用通义千问 / DeepSeek。发票图片在调用 LLM 时会发给对应云厂商，按公司数据政策选择。

### 3.3 常用运维

```powershell
docker compose logs -f
docker compose logs -f backend
docker compose logs -f ocr_worker
docker compose restart backend
docker compose restart ocr_worker
docker compose restart frontend   # 注意是 frontend，不是 fronted
docker compose up -d frontend     # 前端容器退出时单独拉起
```

浏览器仍显示旧错误时，访问 `http://127.0.0.1:15173` 并 `Ctrl+F5`。

**连接串不要混用**：Compose 内后端连 `...@db:5432/...`；本机直接跑 uvicorn 时连 `...@localhost:5435/...`。

## 4. 给财务同事的使用说明（你需要能演示）

### 4.1 报销提交包（优先教这个）

期望目录形态：

```text
张三-报销/
├── 张三报销总表.xlsx          # 文件名以「报销总表.xlsx」结尾
├── 说明.txt                   # 可有，系统忽略
├── 张三2025年4月报销发票/     # 两种月目录名都支持
│   ├── 发票/
│   ├── 补票/                  # 三类来源都可缺省，允许再嵌套
│   └── 支付凭证/
└── 张三-2026年1月-报销/
    └── ...
```

操作：打开「月度资料识别」→ 页面**顶部**选整个 `姓名-报销` 文件夹 → 等待各月识别完成 → 下载带「系统审核」列的总表。

总表审核规则（实现于 `claim_completeness_service.py`）：

- 「时间」只用来落到年-月，不精确到日。
- 空发票号码不拿去核票号。
- 一行默认对应一张发票；事项为「打车」或「本月打车」时，允许该行金额等于当月尚未占用的打车类发票合计。
- 支付截图可以一对多，不独占。
- 打车类合计不做金额差额检查。匹配不到发票则写明「缺发票」。
- 通过只写 `通过`；提交人备注列不改。
- 若把含「报销总表.xlsx」的文件夹误传到单月批次入口，前端会提示改走提交包。

提交包限制（`config.py`）：最多 600 个文件、合计 768 MiB。

### 4.2 单月目录

表单填员工姓名和 `YYYY-MM`，选择一个月度文件夹。路径必须能解析到 `发票` / `补票` / `支付凭证`（可带一层不透明根目录）。扩展名仅 PDF、JPG/JPEG、PNG、MP4/MOV/AVI/MKV。

限制：最多 200 文件、单文件 150 MiB、单批 256 MiB；校验失败整批不落库。

特殊规则（OCR/LLM 之前）：

- 视频：只存元数据，`file_data` 为空，进入人工复核。
- 文件名恰好为 `PDF合并.pdf`：跳过。
- 图片超过 5000 万像素：不解码，人工复核。

### 4.3 单张发票

拖到上传页即可。详情页可看 OCR vs LLM 差异并确认。这条链路的表是 `invoices` / `ocr_results` / `llm_results` / `parsing_diffs`，**不要和月度 `source_documents` 混用**。

### 4.4 导出

| 导出 | 接口 | 内容 |
|------|------|------|
| 批次全量识别结果 | `GET /api/batches/{id}/export/excel` | 一文件一行；终态批次才开放 |
| 审核及分类汇总 | `POST /api/batches/{id}/export/filtered` | 7 张表；分类按交易一行；有记录级缓存 |
| 带系统审核的总表 | `GET /api/packages/{id}/export/claims` | 必须先完成总表审核 |

分类汇总**直接累加交易级识别金额**，不因「主辅凭证」关系改合计。主辅关系只写在 JSON `_reconciliation` 和分类审计明细里，供人看。

## 5. 架构怎么记（改代码前先建立这张图）

```text
浏览器 (15173)
    │  /api 由 Vite 代理到 backend
    ▼
FastAPI routers
    ├─ /api/invoices/*     → invoice_service → OCR + Vision LLM
    ├─ /api/batches/*      → batch_service → document_service
    │                         → 跨文件核对 / 审核分类 / 导出
    ├─ /api/packages/*     → package_ingest → 按月创建 processing_batches
    │                         → claim_completeness（总表审核）
    └─ /api/settings/*     → LLM 配置、公司档案
    ▼
PostgreSQL（原始文件也在库里，不落本地 uploads）

另：ocr_worker 进程串行领取待处理 source_documents
    （配置项 batch_processing_concurrency 尚未接到 worker）
```

分层约定（违反会把项目改乱）：

| 层 | 目录 | 允许做什么 |
|----|------|------------|
| HTTP | `backend/app/routers/` | 校验、调 service、返回；不写识别逻辑 |
| 业务 | `backend/app/services/` | OCR/LLM/比对/审核/拆包；重逻辑只放这里 |
| 表结构 | `backend/app/models/` | 改字段必须同步 schema、前端 types |
| 入参出参 | `backend/app/schemas/` | 不写副作用 |
| 前端通信 | `frontend/src/services/api.ts` | **唯一**调后端的出口 |
| 页面 | `frontend/src/pages/` | 编排 UI；复杂逻辑抽 hooks/components |

全局地图、文件树、状态机见 [`ARCHITECTURE.md`](../ARCHITECTURE.md) 第 3–7 节。

## 7. 业务红线（改识别逻辑前必读）

这些是产品不变量，测试也按它们写。改掉而不改测试，等于把财务口径改 silently。

1. **文件名、目录名、批次月份不能补**日期、金额、对方、号码、单据类型。唯一例外：正文/OCR/模型都得不到摘要时，才用去扩展名后的文件名填 `description`，并标记 `FILENAME_FALLBACK`。
2. 多笔独立交易写入 `extracted_fields_json.records`；只有每笔金额和原文证据都完整时才算文件级金额。
3. 月度提取按类型分流：标准发票/出租车票/行程车票 → 本地规则优先（`RULE_PRIMARY`）；高德行程单 → PDF 坐标表格 → 文本规则 → LLM；支付/订单等 → OCR 文本够则只走文本 LLM，不够再 vision。合法模型结果**不做字段级规则混补**；只有模型不可用/无效或全部关键字段为空时整单 `OCR_RULE_FALLBACK`。
4. 行程单直过要求：每条 TRIP 都有可用起终点和开始时间，且条数与「共计 N 单」一致。
5. 批次 `FAILED` 只表示协调中断或致命失败；单文档失败不会拖垮整批。
6. 启动时把遗留的活动文档标为 `PROCESS_INTERRUPTED`，**必须用户点重新处理**，不会偷偷重跑。
7. `PROCESS_INTERRUPTED`、`MULTIPLE_TRANSACTIONS` 等是 `status_reason`，不是处理状态。
8. 人民币单币种：不提取、不展示币种；`source_documents.currency` 旧列仅兼容保留。
9. 费用类型优先顺序：差旅费、交通费、快递费、物流费、项目成本、招待费、职工福利费；「合计」「会计」等是无效类型。
10. 普通审核导出**不会**补跑缺失的跨文件核对；未核对会在分类审计里标明。需要时点「重新核对主辅凭证」（`POST /api/batches/{id}/reconcile`）。

高德行程单有黄金样本：`backend/tests/fixtures/gaode_itinerary_golden.json`。改行程解析必须跑相关测试。

## 8. 状态机（排障时对照）

单发票：`uploaded → processing → confirmed`，缺字段或 OCR/LLM 冲突则 `reviewing`。

批次：

```text
UPLOADED → PROCESSING → COMPLETED
                     ↘ FAILED（协调中断；可 reprocess）
```

文档：`UPLOADED → PROCESSING → RECOGNIZED | NEEDS_MANUAL_REVIEW | FAILED | SKIPPED`

提交包：`UPLOADED → PROCESSING → COMPLETED | FAILED`。各月批次都进入终态后才会自动做总表审核；也可 `POST /api/packages/{id}/audit` 手动触发。未审核不能导出带「系统审核」列的总表。

前端对活动批次约 **2 秒轮询**一次，终态或离开页面后停止。

| OCR worker **串行**领取；`BATCH_PROCESSING_CONCURRENCY` 未接入 | 大月目录会慢；不要以为改配置就真的并行了 |
| 无 Alembic | 多环境 schema 靠启动脚本，复杂变更容易漏 |
| 批次文档无字段编辑 API | 财务发现识别错了，只能重处理或在 Excel 里改，不能在页面改字段 |
| 原始文件在 PostgreSQL | 库会胀；备份等于备份 Docker 卷 `postgres_data` |
| 前端容器有时会退出 | 见 `caozuo.md`，`docker compose up -d frontend` |
| 历史密钥曾进过 `.env.example` | 已改占位符；若供应商控制台仍有旧 Key，应轮换 |
| worker 用 advisory lock | 不要起两个 ocr_worker 实例指望加速 |

路线图上尚未做的：发票真伪（税务 API）、移动端、审批/ERP。若业务优先项是「识别更准」或「总表规则更贴财务习惯」，应先开新 plan，而不是直接改 Prompt。

## 12. 排障速查

| 现象 | 先查 |
|------|------|
| 前端打不开 | `docker compose ps` 看 `invoice_frontend` 是否 Exit；重启后强制刷新 |
| 上传后一直处理中 | `docker compose logs -f ocr_worker`；确认 LLM Key；看批次是否 `PROCESS_INTERRUPTED` |
| 月度识别质量差 | 是否配置了可用 Vision/文本模型；支付类是否 OCR 过稀；行程单是否坐标层完整 |
| 总表无法导出 | 各月批次是否终态；是否已 `audit`；接口会返回「尚未完成总表审核」 |
| 分类合计和直觉不符 | 合计用的是识别金额，不是主辅去重后的建议计入金额 |
| 导出很慢 | 审核分类有记录级缓存；Prompt/档案/辅助表/模型一变会失效重算 |
| 改完代码容器没变化 | backend/frontend 都是 bind mount；backend 无 `--reload` 时需 `docker compose restart backend` |
| 数据库连不上 | 端口是 **5435** 不是 5432；健康检查未通过时 backend 不会起来 |

```text
# 健康
```
